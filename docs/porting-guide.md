# SNNUAutoLogin-GUI 开发迁移指南

本文面向希望把本项目改编为其他学校版本的开发者，说明当前适配的门户、需要调查的协议和具体修改位置。依据当前仓库源码整理，不代表已验证其他学校兼容。

## 1. 当前支持什么门户

本项目针对陕西师范大学校园网网页认证门户开发。用户连接校园网后，通过网页输入账号、密码并选择运营商出口；程序通过 HTTP 请求复现这一过程，再提供巡检、重连和设备管理。

| 项目 | 当前实现 |
| --- | --- |
| 门户主机 | `202.117.144.205` |
| 认证根路径 | `http://主机:端口/snnuportal/` |
| 登录方式 | POST，`application/x-www-form-urlencoded` |
| 登录字段 | `account`、`password`、可选的 `yys` |
| 运营商值 | `mobile`、`unicom`、`telecom`；校园网出口不主动设置该字段 |
| 登录入口 | 读取表单 action，并有 `login`、`login.jsp` 回退地址 |
| 在线状态 | 请求 `userstatus.jsp`，解析“当前登录账号”“当前IP”“登录时间” |
| 页面编码 | 外层优先按 GB18030 解码，包含部分 UTF-8 回退处理 |
| 验证码 | 识别图片和输入字段，由用户手动填写 |
| 设备列表 | 从状态页提取 iframe，再解析其中的 UTF-8 HTML 表格 |
| 本机断开 | 请求 `logoff` |
| 其他设备下线 | 使用设备会话标识及页面查询串中的令牌构造请求 |

登录前会读取隐藏字段，并补充登录页 URL 中的参数，不能随意省略。当前代码直接将密码放入表单，未实现其他门户可能要求的 JavaScript 加密、challenge 签名或专用认证算法。

**端口与运营商不是同一概念。** 当前程序读取入口返回的 JavaScript 跳转，提取服务器分配的端口；运营商由 `yys` 表示，不能假定一个端口固定对应某个运营商。

判断兼容性应比较实际请求流程和数据结构，不能只看页面外观或厂商名称。

## 2. 判断迁移范围

| 目标门户 | 迁移工作 |
| --- | --- |
| 协议相同，仅部署地址不同 | 修改地址、路径、端口和默认配置 |
| HTML 表单，但字段或页面不同 | 调整表单构造、状态解析和错误识别 |
| JSON API、JavaScript 加密或 challenge | 实现相应认证请求和结果解析 |
| 跨主机统一身份认证 | 适配会话、令牌、跳转及允许访问的主机 |
| 短信、扫码或其他交互验证 | 增加交互，重新评估无人值守重连能力 |
| 802.1X 或专用客户端协议 | 现有 HTTP 登录逻辑不能直接使用，需要独立实现 |

界面、托盘、自启动和设置保存通常可以复用。巡检、端口发现和同时在线设备监测是否能复用，要根据目标门户判断。

## 3. 迁移前收集信息

在自己的设备和账号上，打开浏览器开发者工具的 Network 面板，开启“保留日志”，从未认证状态完成一次正常登录。记录：

1. 入口 URL、跳转后的协议、主机、路径和端口。
2. 登录请求的方法、内容类型、字段、Cookie 及前置请求。
3. 账号是否需要运营商后缀、认证域或其他前后缀。
4. 密码是否原样提交；若不是，核对页面脚本，不凭字符串外观猜算法。
5. 令牌、challenge、接入设备参数和时间戳从哪里取得，何时刷新。
6. 状态查询、本机退出、设备列表和其他设备下线的接口。
7. 密码错误、验证码错误、会话过期的响应。
8. 登录页、状态页、设备页和表单提交的实际编码。

保存脱敏页面及响应作为测试样本，不要将密码、Cookie、有效令牌提交到仓库，也不要把一次抓取的动态值写死在代码中。

## 4. 具体修改位置

### 4.1 门户地址和端口发现

主要文件：`Services/PortalClient.cs`、`Services/PortalPortDiscovery.cs`。

检查 `PortalHost`、`RootFor`、`DiscoveryUrl`、`KnownPorts` 和 `DiscoverAssignedPortAsync`。固定端口门户应调整发现流程；HTTPS 门户应同步修改地址协议。

项目多处使用 `8603` 作为默认或回退值，包括设置、配置解析、登录协调和设备管理。应逐一检查，避免新端口被旧配置校验替换。可从以下搜索开始，不要不分用途地全局替换：

```powershell
rg -n '202\.117\.144\.205|8603|snnuportal' Services Shared Linux tests
```

当前按端口隔离 HttpClient 和 Cookie 容器，防止同主机不同端口串用会话。目标门户的会话边界不同，应按实测调整。

### 4.2 登录请求与账号规则

修改 `Services/PortalClient.cs` 中的 `LoadLoginPageAsync`、`ParseLoginPage`、`LoginInternalAsync`、`BuildFormBody` 和 `ExtractError`。

当前固定提交 `account`、`password` 和可选的 `yys`，还会识别并剥离账号中的部分运营商后缀。字段变化时，应同时修改表单赋值、隐藏字段排除规则和相关解析，避免重复提交旧字段。

若目标门户使用 GET、JSON、加密密码或 challenge，应按真实请求重写流程。现有解析器不会执行 JavaScript，也不是通用浏览器；找到表单不代表能完成认证。

### 4.3 在线状态、验证码与编码

在线判断不只在 `GetStatusAsync` 中，登录响应和登录页读取中也包含“当前登录账号”的判断。应统一修改，建议集中为一个状态解析方法。HTTP 200 不能单独作为认证成功依据。

验证码需核对输入字段、图片地址、刷新方式及 Cookie 会话。当前是用户手动输入，不能保证出现验证码后仍可无人值守重连。

页面解码和表单编码应分别验证。除调整 GB18030/UTF-8 解码策略，还要检查 `BuildFormBody` 的百分号编码是否与浏览器实际提交一致。

### 4.4 请求地址限制和代理

文件：`Shared/PortalRequestHandler.cs`。

当前请求限于指定门户主机；表单提交还要求协议和端口符合来源限制。跨主机认证应为实际参与认证的地址设置明确允许范围，并核对重定向规则，不要直接删除限制，以免凭据被提交到意外地址。

当前设置 `UseProxy = false`，门户需要校园网直连时应保留。浏览器正常而软件失败时，也要排查代理和路由差异。

### 4.5 网卡识别与联网探测

| 文件 | 检查内容 |
| --- | --- |
| `Services/NetworkAccessService.cs` | `RouteProbeHost` 仍为原学校地址 |
| `Linux/Agent/LinuxNetworkAccess.cs` | 路由查询目标同样写有原学校地址 |
| `Services/NetworkProbeService.cs` | 默认校内目标 `www.snnu.edu.cn` 及外网目标 |
| `Services/ConnectionProfileResolver.cs` | 连接规则和端口回退 |
| `Shared/AppSettings.cs` | 默认端口和探测设置 |
| `Services/CredentialStore.cs` | 已保存配置的校验、回退和迁移 |

只改认证地址会遗漏路由与探测，可能选错网络或误判状态。应区分“门户可达”“校内资源可达”和“能够访问外网”，不要把单个探测目标失败直接等同于账号掉线。

### 4.6 设备管理与同时在线设备监测

主要文件：`Services/DeviceListParser.cs`、`Services/PortalClient.cs`、`Services/DeviceManager.cs`、`Services/IOnlineDevicePortal.cs` 和 `Services/DeviceGuardService.cs`。

当前依赖特定 iframe、表格列顺序和 `dm(...)` 会话标识；强制下线还保留页面查询串中的会话参数。需要分别确认：

- 设备列表来自 HTML、iframe 还是 JSON。
- 如何识别本机、取得其他设备会话标识。
- 本机断开与其他设备下线分别使用什么接口和请求方法。
- 哪些令牌必须保留，何时失效。
- 主动断开后自动重连是否符合预期。

目标门户没有设备管理能力时，应隐藏或禁用相关入口和依赖它的守卫逻辑，不能把读取失败显示成零台设备。守卫涉及主动断开和重登，应在基础认证稳定后再启用。

### 4.7 界面、发布和更新

修改学校名称、运营商选项、门户链接、帮助文案、图标和安装包信息。认证请求仍放在服务层，界面通过现有运行时和服务获取结果。

检查 `Services/ReleaseUpdateCheck.cs` 的更新来源，避免改编版引导用户下载原版。同时维护 Windows 和 Linux 时，应核对共享核心、平台网卡识别和打包配置。

## 5. 推荐实施顺序

1. 保存脱敏请求、页面及异常响应样本。
2. 适配入口、端口发现与请求地址限制。
3. 实现手动登录、在线查询和本机退出。
4. 验证账号规则、会话、错误提示、编码和验证码。
5. 接入巡检、网络变化处理与断线重连。
6. 按门户能力适配设备列表和守卫。
7. 更新默认设置、旧配置迁移、品牌及发布配置。

先让最小认证流程可靠运行，再启用主动断开或重登功能。长期支持多所学校时，建议把地址、字段、状态解析和设备管理能力封装为门户适配层，避免向同一个客户端不断追加学校判断。

## 6. 验证迁移结果

更新现有测试中的门户样本和期望值，新增覆盖真实差异的用例。根据修改范围，在仓库根目录执行：

```powershell
dotnet run --project tests/DeviceListTests -c Release
dotnet run --project tests/StartupTests -c Release
dotnet run --project tests/CredentialTests -c Release
dotnet run --project tests/GuardTests -c Release
dotnet build SNNUAutoLogin.csproj -c Release
```

涉及共享核心或 Linux 时，再运行 `tests/LinuxCoreTests`，并按 `Linux/README.md` 检查 SDK 和构建要求。环境要求以当前工程文件和平台说明为准。

自动测试不能代替目标校园网实测。至少验收：

- 正确账号可登录并访问预期网络，不把 HTTP 成功误判为认证成功。
- 密码错误、验证码失效、会话过期时提示准确，不会持续快速重试。
- 已在线时不会反复提交登录。
- 断网恢复、休眠唤醒和 IP 变化后能重新判断状态。
- 主动退出与自动重连行为符合设计。
- 非校园网环境不会持续错误认证。
- 设备列表异常时不会误踢设备或触发守卫循环。
- 日志不包含密码、有效令牌和完整会话信息。

## 7. 从未知门户到认证 MVP：实际探索流程

前面的修改清单建立在“已经知道协议”的前提上。第一次适配往往最耗时的恰恰是确定协议：最终几行请求代码，可能来自很多轮失败对比。本节给出建议的调查方法，不是对本项目第一版开发历史的复述；没有开发记录支持的尝试，不应当作已发生的事实。

### 7.1 先确定实验环境和基线

先关闭自动登录、自动重连及会主动断开的设备守卫，避免后台操作污染实验。记录网络类型、当前网卡、IP、系统代理和门户地址。一次实验尽量只使用一条接入网络；不要同时更换账号、网络和请求代码。

必须先确认：同一设备、同一网络下，浏览器可以从未认证状态完成登录，并实际访问预期资源。浏览器本身不能登录时，先区分账号、欠费、网络接入和门户故障，不要立刻修改程序。

每轮实验记录如下信息：

| 信息 | 示例内容 |
| --- | --- |
| 初始状态 | 已退出认证；浏览器是否仍保留 Cookie |
| 接入环境 | 有线或无线、网卡、IP、代理状态 |
| 本轮假设 | 登录必须先获取 Cookie |
| 唯一变化 | 增加入口 GET，其他请求保持一致 |
| 观测结果 | 响应码、最终地址、脱敏响应摘要、状态查询和联网结果 |
| 结论 | 支持、否定或证据不足；下一步验证什么 |

“这次成功了”只能证明这次组合可行，不能证明每个参数都有必要，也不能证明它在新会话中仍有效。

### 7.2 抓完整请求链，不只抓最后一次 POST

从未认证状态开始，在浏览器 Network 中保留日志，依次记录入口请求、HTTP 跳转、页面脚本触发的请求、登录提交、登录后状态查询。HTTP 重定向和 JavaScript 跳转不是一回事：普通 HTTP 客户端不会执行 `window.location`。

建议给请求编号，写出一条实际观测到的流程，例如：

```text
入口 → 分配接入地址 → 获取登录页与 Cookie
     → 读取隐藏参数 → 提交认证 → 查询状态 → 验证联网
```

这只是调查模板。目标门户没有的步骤不要强加，有额外步骤则补上。特别检查浏览器是否使用了之前已建立的会话：一份看似独立成功的 POST，可能依赖更早获取的 Cookie。

**通过标准：** 能解释每个关键参数的来源，以及哪些响应产生了下一步所需的 Cookie、令牌或地址。

### 7.3 在独立请求工具中复现，再逐项缩减

可先使用浏览器“复制为 cURL”得到请求基线。在本机妥善处理其中的凭据，不要直接贴进公开问题或提交到仓库。复制请求不是最终实现，只是对照实验。

先验证复制的请求能否在明确的未认证状态下成功。如果必须带上旧 Cookie 才成功，继续调查如何从新会话获取它；不要把旧 Cookie 硬编码。若令牌一次性有效，应重新执行获取步骤，而不是反复重放相同提交。

基线成功后，每次只移除或改变一类内容：普通请求头、Referer/Origin、Cookie、隐藏字段、URL 参数。某项删除后失败，再恢复并重测。服务端可能暂时沿用旧认证状态，所以每轮都要确认初始状态，不能用已在线结果证明新请求有效。

不要一次删除所有“看起来没用”的字段，也不要无依据地补齐大量浏览器请求头；两种做法都会使结论难以定位。

**通过标准：** 可以从新会话重复执行完整流程，并得到已认证状态和预期联网结果，而不是依赖某次抓包留下的临时值。

### 7.4 编写最小认证程序，暂不接 GUI

先做一个只执行一次认证流程的小程序，顺序完成：入口发现、建立会话、取动态参数、提交、查状态、探测网络。关闭定时器和后台重试，保留取消及超时能力。验证码若存在，允许手动输入，并确保取图与提交使用同一会话。

日志记录步骤、耗时、状态码、跳转目标和经过脱敏的解析结果，不记录密码、有效 Cookie、令牌或包含这些信息的完整 URL。必要时在本地保存脱敏响应，避免只剩一句“登录失败”而无法分析。

现有项目的 `PortalClient` 可以作为结构参考，但不要为了复用旧代码而强迫新门户使用旧字段、旧端口或旧成功标识。

**通过标准：** 多次从未认证状态登录成功；错误密码不会误报成功；超时和门户异常能明确返回失败；新会话不依赖手工复制的旧参数。

### 7.5 分别验证三种“成功”

| 层次 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| HTTP 请求成功 | 收到了服务器响应 | 账号已通过认证 |
| 门户报告在线 | 门户认为某个账号或出口在线 | 当前应用网络路径一定可访问外网 |
| 目标资源可达 | 当前路径可访问所测资源 | 全部网络正常，或一定是本次提交建立的认证 |

登录响应提示成功后，再查询状态，核对可取得的账号和 IP，并访问预期的校内、外网资源。探测要检查是否被重定向到认证页，不能只看状态码。账号、出口或 IP 不符合预期时，检查旧会话和多网卡路由。

ICMP 不通可能只是目标禁 ping；单个网站失败也可能是网站故障。为各类结果保留不同诊断信息，不要全部显示成“密码错误”或“未登录”。

### 7.6 从单次成功走向自动重连

单次认证 MVP 通过后，再引入巡检和网络变化监听。首先明确状态与转换：未接入网络、门户不可达、未认证、认证中、等待验证码、门户在线、联网异常及用户主动退出。

需要明确以下策略：

- 手动登录、定时巡检和网络事件同时触发时，只允许一个认证流程操作当前会话。
- 网络切换后，取消旧任务，重新发现入口并获取参数，不复用旧网卡上的挑战值。
- 认证后给状态更新留出合理确认过程，避免立即认定失败并再次提交。
- 密码错误、账号限制等明确失败等待用户处理；暂时网络错误使用有间隔且有上限的重试。
- 等待验证码时，不让其他巡检请求反复刷新验证码会话。
- 主动退出后是否暂停重连必须有明确产品行为，不能让用户陷入“刚断开又自动连上”。

这些是迁移时要验证的设计要求，不代表现有所有模块已经天然满足目标门户。

### 7.7 最后接入界面及高级功能

把已验证的认证能力接入现有服务和运行时，再显示到 GUI。先验证界面能准确反映认证中、等待输入和失败原因，再接设备管理与守卫。

设备下线具有实际副作用，必须先验证只读列表及本机识别，再测试明确选中的会话；不要把同时在线设备监测当作验证基础登录的工具。

## 8. 常见失败：按证据排查

| 现象 | 优先检查 | 建议的下一次实验 |
| --- | --- | --- |
| 浏览器成功，复制请求失败 | 旧 Cookie、一次性令牌、前置请求缺失 | 新会话重新抓取并按顺序执行 |
| 请求工具成功，程序失败 | 方法、URL、正文原始字节、Cookie、重定向差异 | 对比两边实际发出的请求，逐项验证 |
| 收到 200，但仍是登录页面 | 表单入口错误、字段错误、认证被拒绝 | 保存脱敏响应并查看页面错误及下一次请求 |
| 提示成功，但不能上网 | 旧会话、账号/IP 不符、路由、探测重定向 | 查状态并分别验证校内和外网 |
| 状态页有中文却解析不到 | 编码、标点、HTML 结构或成功标识变化 | 对照原始字节与解码文本，单独测试解析 |
| 验证码一直错误 | 取图与提交会话不同、后台刷新、码已过期 | 暂停巡检，用同一客户端取图后立即提交 |
| 重启软件后才失败 | 临时 Cookie/令牌未重新建立、默认配置回退 | 清楚记录启动流程，从空会话重新登录 |
| 单次成功，自动重连不稳定 | 并发、旧参数、网络尚未就绪、快速重试 | 关闭其他触发源，逐个恢复并记录时序 |
| 状态能读，设备列表失败 | iframe 地址、主机限制、代理、编码、令牌 | 单独检查设备页请求及响应，不先改表格正则 |
| 修改默认端口后仍回到旧值 | 保存配置、校验和回退分散 | 同时测试新配置及旧配置加载路径 |

排查遵循三个原则：先保留可复现基线；每次只验证一个假设；无法区分原因时明确标记证据不足。避免在缺少响应记录时反复猜字段、改正则或延长超时。

## 9. MVP 完成标准与交付记录

“程序显示登录成功”还不够。认证 MVP 至少应提供：

- 一份从新会话开始的协议流程说明，标明地址、字段、动态参数来源和会话边界。
- 可重复运行的单次认证流程，以及脱敏的成功、失败响应样本。
- 在线判断与联网探测的区别说明，明确哪些网络环境已实测。
- 错误密码、超时、会话过期和验证码等实际出现分支的处理结果。
- 未解决问题清单，例如暂不支持的接入网络或需要人工完成的认证步骤。

自动重连和 GUI 属于后续集成验收；设备管理、守卫则是额外能力。只有把每个阶段的证据保存下来，后来者才能复用已经验证的结论，而不是重新经历同样的试错。
